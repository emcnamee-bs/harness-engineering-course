00

Orientation: what a harness actually is

map, no build

What

"Harness engineering" is a term that crystallized in early 2026 (Mitchell Hashimoto's essay on permanently fixing an agent's environment rather than its prompt) and was picked up within weeks by both Anthropic and OpenAI's engineering blogs. Martin Fowler's team gives the sharpest model: a harness regulates a model through two control types — guides (feedforward: docs, examples, tool descriptions that steer behavior before generation) and sensors (feedback: linters, tests, evals that catch problems after generation) — each implemented either computationally (deterministic, fast, brittle) or inferentially (LLM-judged, flexible, noisy).

Why it exists

Prompting a smarter model gets you diminishing returns fast. Nearly all real gains in agent capability since 2024 have come from the scaffolding, not the weights — better tool descriptions, tighter context management, real eval loops. The industry now treats harness quality, not model choice, as the main lever a team actually controls.

🔍 Field exercise

Goal A one-page personal map of the guide/sensor, computational/inferential taxonomy, with a real example from a system you already use in each of the four boxes — so the vocabulary sticks to something concrete before module 01 asks you to build one from scratch.
Setup

None — no code, no installs. Just a text editor or a sheet of paper and access to the Claude Code session you're already using.

Steps
  1. Draw a 2×2 grid: rows GUIDE / SENSOR, columns COMPUTATIONAL / INFERENTIAL.
  2. Open ~/.claude/CLAUDE.md in a text editor and find the "Autonomous agent orchestration" guardrails section near the bottom.
  3. For each of its 9 numbered rules, decide: does it steer behavior before the model acts (a guide) or catch a problem after (a sensor)? Is the check itself a deterministic bit of code (computational) or does it require judgment/an LLM call (inferential)? Write the rule number into the matching box.
  4. Do the same for two things this Claude Code session already does to you: the permission prompt that appears before a risky command, and the auto-generated memory files under memory/MEMORY.md.
  5. You should end with at least one real example filled into all four boxes of the grid.
check You can point at one real mechanism in this environment for each of the four boxes — four concrete examples, not four definitions restated in your own words.
01

The bare loop

structure

What

An agent is, underneath everything, a while loop around an API call: send messages, get a response, decide whether it's asking for a tool or giving a final answer, act, feed the result back in, repeat. This is the ReAct pattern (Yao et al. 2022) that every harness below still runs on.

Why it exists

Build this ugly first. Skipping straight to a framework (LangGraph, CrewAI) hides the one fact you need burned in: there is no magic control flow, only text going in and text coming back out, and your code deciding what that text means.

🛠 Build

Goal One script, agent.py, that holds a multi-turn conversation with the model, recognizes when its reply is asking to run a tool (by spotting a plain-text tag you invented yourself), actually runs that tool, and stops only when the model answers with no tag at all. No SDK tool-calling feature yet — that's module 02. Here you parse plain text by hand so you feel exactly why that's fragile.
Environment setup 
mkdir -p ~/harness-course/01-bare-loop && cd ~/harness-course/01-bare-loop
python3 -m venv .venv && source .venv/bin/activate
pip3 install anthropic
export ANTHROPIC_API_KEY=sk-...          # from console.claude.com → API Keys
printf '4\n15\n23\n8\n' > fileA.txt      # a test fixture with a known answer (sums to 50)
Steps
  1. Create agent.py in that folder.
  2. Write a system prompt string that tells the model the exact tag format to use when it wants a tool, e.g. <tool>read_file(fileA.txt)</tool>, and says plainly: "if you don't need a tool, just answer in plain text, with no tag."
  3. Write call_model(messages): one call to client.messages.create(...) passing your system prompt and the message list, returning the reply text.
  4. Write parse(reply): use a regex (e.g. r"<tool>(\w+)\(([^)]*)\)</tool>") to pull out (name, args) if a tag is present, or return None if it isn't.
  5. Write run_tool(name, args): for read_file, actually open and return the named file's contents; for add, actually sum the numeric args. Anything else, return a plain string saying so.
  6. Wire the loop below, save, and run python3 agent.py.
  7. Ask it: "Read fileA.txt, then compute the sum of the numbers in it."
while True:
    reply = call_model(messages)
    if "<tool>" in reply:
        result = run_tool(parse(reply))
        messages.append({"role":"assistant","content":reply})
        messages.append({"role":"user","content":f"OBSERVATION: {result}"})
    else:
        return reply
check You should see the loop fire exactly twice — one tool call, one final answer — and the final answer should say 50. If the model wraps its tag in extra prose and your regex misses it, that's not a bug in the exercise — that's the fragility this module exists to make you feel.
02

Tool interfaces (the ACI)

guideinferential

What

Replace text-tag parsing with real structured tool schemas (JSON Schema, native function-calling). Princeton's SWE-agent calls this the Agent-Computer Interface — the tool surface is a UI you're designing, just for a model instead of a human. Their line-windowed file viewer with built-in linting was the difference between failing and passing real tasks.

Why it exists

The error message a tool returns is a design surface, not an afterthought — a vague Error: failed sends the model down a dead end; a precise Error: line 42 not found, file has 30 lines lets it self-correct next turn.

🛠 Build

Goal The same loop as module 01, but the model now calls tools through your provider's real function-calling feature instead of a text tag you invented — and you'll have hard numbers showing that a tool's error message changes how fast the model recovers from a mistake.
Environment setup 
mkdir -p ~/harness-course/02-tool-interfaces && cd ~/harness-course/02-tool-interfaces
cp ../01-bare-loop/fileA.txt .
source ../01-bare-loop/.venv/bin/activate   # reuse the venv from module 01
Steps
  1. Define 3 tools as JSON Schema objects for the tools=[...] parameter of messages.create: read_file(path), write_file(path, content), run_shell(command).
  2. Replace your module-01 regex loop: after each call, check response.stop_reason — if it's "tool_use", find the tool_use block(s) in response.content and read .name / .input directly (no parsing needed, the SDK already did it).
  3. Reply with a tool_result content block containing your tool's output, keyed to the tool call's id.
  4. Make two versions of read_file's failure path: version A returns the bare string "error" when the file doesn't exist; version B returns something like "File 'nope.txt' not found. Files available here: fileA.txt".
  5. Ask the agent to read a file that doesn't exist, once against version A and once against version B. Count how many turns it takes each version to either recover (try a real filename) or give up.
  6. Now do Anthropic's Prototype → Evaluate → Collaborate step: paste your read_file tool's JSON Schema description back to the model in a fresh conversation and ask it to critique the description and rewrite it. Swap in its rewrite and re-run step 5.
check Version B (the precise error) recovers in fewer turns than version A on the same failing input, and the model's self-rewritten description performs at least as well as yours — you've now measured, not assumed, that tool design changes agent behavior.
03

Eval harness — build this early

sensorcomputational

What

Five to fifty hand-written tasks, each with an unambiguous pass/fail check, run against your loop. Three grader types: code-based (fast, brittle), model-based (flexible, noisy), human (slow, gold standard). Grade the outcome, not the path the agent took to get there.

Why it exists

Every module from here on changes your agent's behavior. Without this you're guessing whether a change helped. Anthropic's own eval guidance puts this before, not after, the fancy features — you can't tune what you can't score.

🛠 Build

Goal A folder of 5 small tasks plus one runner script, run_evals.py, that fires each task through your module-02 agent and prints a pass/fail table — so from here on, "did that change help?" has a number attached instead of a guess.
Environment setup 
mkdir -p ~/harness-course/03-eval-harness && cd ~/harness-course/03-eval-harness
cp ../02-tool-interfaces/*.py .
cp ../01-bare-loop/fileA.txt .
source ../01-bare-loop/.venv/bin/activate   # no new packages needed — plain Python is enough
Steps
  1. Write down 5 short tasks in plain English and their exact expected outcome. Reuse real ones from modules 01–02 if you have them (e.g. "read fileA.txt, sum it → 50"; "read a nonexistent file → agent reports the error and doesn't crash").
  2. For each task, write a tiny Python function check_N(final_answer: str) -> bool that returns True only if the answer is actually correct (e.g. "50" in final_answer).
  3. Create tasks.py: a list of {"prompt": ..., "check": check_fn} dicts, one per task.
  4. Create run_evals.py: import your module-02 run() function, loop over tasks.py, call run(prompt), apply the matching check, and print a table like PASS task 1 / FAIL task 3.
  5. Run it once. Record the score as your baseline (e.g. "5/5" or "4/5").
  6. Now deliberately revert the tool-description improvement you made in module 02 back to the vague version, and re-run run_evals.py.
check The score visibly drops after the revert. If it doesn't, your 5 tasks aren't sensitive enough to the thing you're trying to measure — pick a task that actually exercises the failure path you improved.
04

Context management

guidecomputational

What

Three techniques: compaction (summarize older turns as you approach the limit, discard stale tool output), structured notes (durable facts written to disk, outside the window entirely), and just-in-time retrieval (fetch on demand instead of preloading). Separately: prompt caching — a prefix-matched cache, up to 4 breakpoints per request, ~10× cheaper on a hit.

Why it exists

A nominal 200K-token window degrades in practice past roughly 60–80K effective tokens. Long tasks silently get dumber long before they hit the hard limit unless something actively curates what stays.

🛠 Build

Goal A version of your loop that survives a task long enough to have blown up module 02's context — because it compacts old turns into a summary before that happens — and a printed log showing when compaction fires and how much cheaper repeated calls get with caching.
Environment setup 
mkdir -p ~/harness-course/04-context && cd ~/harness-course/04-context
cp ../02-tool-interfaces/*.py .
source ../01-bare-loop/.venv/bin/activate
printf '11\n7\n19\n' > fileB.txt
printf '3\n42\n5\n1\n' > fileC.txt
Steps
  1. Every response from the Anthropic API includes token counts on response.usage. After each call_model() call, add response.usage.input_tokens to a running total and print it.
  2. Pick a low threshold for testing, e.g. THRESHOLD = 3000, so you can trigger compaction without needing a huge real task.
  3. When the running total crosses THRESHOLD: take every message except the last 2, send them to the model with the instruction "Summarize the above conversation concisely, keeping any facts still needed to finish the task," and replace them in your messages list with that one summary message.
  4. Give it a task that forces enough back-and-forth to cross your threshold: "Read fileA.txt, fileB.txt, and fileC.txt one at a time, then tell me the sum of all three files combined" (answer: 50 + 37 + 51 = 138).
  5. Print a line every time compaction actually fires, so you can watch it happen mid-task.
  6. (Optional, needs a paid API key with usage past the free tier) Add cache_control: {"type": "ephemeral"} to your system prompt block and compare response.usage.cache_read_input_tokens across repeated runs.
if running_total_tokens > THRESHOLD:
    old, recent = messages[:-2], messages[-2:]
    summary = call_model([*old, {"role":"user","content":"Summarize the above concisely."}])
    messages = [{"role":"user","content":f"[compacted summary] {summary}"}, *recent]
    print("[compaction fired]")
check The three-file task completes with the correct total (138) even though your running total crossed THRESHOLD partway through — and your console shows at least one "[compaction fired]" line before the final answer.
05

Permissions & sandboxing

sensorcomputational

What

Claude Code's real shipped model: filesystem reads are deny-then-allow (open by default, selectively blocked); writes are allow-only (closed by default, selectively opened). Network is allow-only through a local proxy enforcing a domain list. Nothing reaches disk or network unmediated.

Why it exists

An unsupervised agent that can write anywhere and call anything is a liability, not a feature. Anthropic reports this exact pattern cut permission-prompt interruptions by 84% in production — tight rules mean fewer stops, not more.

🛠 Build

Goal Your write_file and run_shell tools refuse to act outside one folder you designate as the sandbox, tell the model exactly why when they refuse, and log every allow/deny decision — so nothing outside that folder is ever touched, even if the model asks for it.
Environment setup 
mkdir -p ~/harness-course/05-permissions/sandbox && cd ~/harness-course/05-permissions
cp ../02-tool-interfaces/*.py .
source ../01-bare-loop/.venv/bin/activate
Steps
  1. Decide SANDBOX = os.path.realpath("./sandbox") — the one directory writes are allowed inside.
  2. Before write_file executes, resolve its target path with os.path.realpath() and check it starts with SANDBOX. If it doesn't, skip the write entirely and return an observation like: "Denied: writes are only allowed inside sandbox/. You asked for '../../etc/passwd'."
  3. Give run_shell a small allow-list of command names it may run (e.g. ["ls", "cat", "python3"]); reject anything else with a clear reason, e.g. "Denied: 'rm' is not on the allowed command list."
  4. Append every decision — allowed or denied, and the reason — as one line to permissions.log.
  5. Ask the agent to write a file outside sandbox/ on purpose (e.g. "write hello.txt to the parent directory"). Watch what it does on its next turn after being denied.
check The write outside sandbox/ is blocked, permissions.log records why, and the model's very next message proposes writing inside sandbox/ instead — proof the denial reason gave it enough to work with.
06

Sub-agent fan-out

structure

What

Split a task across workers that each get a genuinely fresh, isolated context — no parent history, no sibling history — and return only a condensed summary upward. This is the exact mechanism behind the fork/subagent tool available in this very session.

Why it exists

Context isolation beats context sharing. A parent that reads every subagent's full transcript re-inherits all their token cost and noise; a parent that reads only their summaries stays cheap and focused no matter how much work happened underneath.

🛠 Build

Goal One parent script that hands 3 independent chunks of one bigger task to 3 separate, empty-history copies of your module-02 agent, and only ever reads back one short summary from each — proving the parent's own context stays small no matter how much work happened underneath.
Environment setup 
mkdir -p ~/harness-course/06-subagents && cd ~/harness-course/06-subagents
cp ../02-tool-interfaces/*.py .
source ../01-bare-loop/.venv/bin/activate
printf 'The quarterly report is due Friday.\n' > noteA.txt
printf 'Revenue grew 12 percent versus last quarter.\n' > noteB.txt
printf 'Three new hires start next month.\n' > noteC.txt
Steps
  1. Write run_subagent(task_prompt: str) -> str: it creates a brand-new, empty messages = [{"role": "user", "content": task_prompt}] list (no shared history with anything else) and runs your module-02 loop to completion on just that, returning the final answer string only.
  2. In a separate parent.py, call run_subagent() three times — once per note file — with a prompt like "Summarize noteA.txt in one sentence." for each.
  3. Keep only the returned one-sentence strings in the parent's own message list. Never append a subagent's internal tool calls or reasoning to the parent's history.
  4. Have the parent make one final call combining the three summaries into a single paragraph.
  5. Print the parent's own cumulative input_tokens total (from module 04) next to the combined token total across all 3 subagents, so you can see the split.
check The parent's own token count stays small and flat regardless of how many tool calls each subagent needed internally — only the combining step and the 3 short summaries ever entered the parent's context.
07

Persistent memory

guidecomputational

What

Durable facts written to disk outside any single conversation, plus a small index file pointing into them — structurally identical to the MEMORY.md + per-topic-file pattern already indexing facts for this very assistant.

Why it exists

A process restart or a fresh conversation shouldn't mean total amnesia. Long-running agent designs split cleanly into a short-lived reasoning context and a long-lived, append-only memory store that survives it.

🛠 Build

Goal A memory/ folder that survives your Python process exiting — you'll kill the script, start a completely new one with an empty conversation, and it still knows a fact you told it in the previous run.
Environment setup 
mkdir -p ~/harness-course/07-memory/memory && cd ~/harness-course/07-memory
cp ../02-tool-interfaces/*.py .
source ../01-bare-loop/.venv/bin/activate
touch memory/index.md
Steps
  1. Add a new tool, save_memory(title: str, content: str), that writes a file memory/<title>.md and appends one line to memory/index.md, e.g. "- title: one-line summary".
  2. At the very top of your script, before the first call_model() call, read memory/index.md (not the individual fact files) and append its contents to your system prompt under a heading like "Things you already know from past runs:".
  3. Run the script. Tell the agent: "Remember that fileA.txt sums to 50." Confirm it calls save_memory and that memory/index.md now has a new line.
  4. Fully quit the script (Ctrl+C, or let it return).
  5. Run python3 agent.py again as a brand-new process with an empty messages list. Ask: "What does fileA.txt sum to?" — without mentioning the earlier run.
check The fresh process answers "50" correctly, and that fact never appears anywhere in the new conversation's own messages list — it only got there via memory/index.md loaded into the system prompt.
08

Tool ecosystem via MCP

structure

What

The Model Context Protocol standardizes the tool boundary itself, so a tool built once works from any compliant client. Past a handful of tools, the code-execution-with-MCP pattern — expose tools as an explorable code API the model writes small programs against, instead of preloading every schema — cut one real case from 150K to 2K context tokens.

Why it exists

Ad hoc tools don't compose across projects or agents. A standard protocol means the toy server you build today is usable from Claude Code, an MCP inspector, or your own harness — the same artifact, three consumers.

🛠 Build

Goal One small MCP server file exposing 2 tools, which you can poke at from the official inspector UI AND call from your own agent loop — proving the same server works from two independently-written clients with zero server-side changes.
Environment setup 
mkdir -p ~/harness-course/08-mcp && cd ~/harness-course/08-mcp
source ../01-bare-loop/.venv/bin/activate
pip3 install mcp
# the inspector is a Node tool — needs Node.js/npx installed separately
cp ../01-bare-loop/fileA.txt .
Steps
  1. Follow the official MCP Python SDK's quickstart (modelcontextprotocol.io) to scaffold server.py as a stdio server. This part is mostly copy-from-the-docs — the lesson here is the protocol boundary, not hand-rolling a server framework.
  2. Expose exactly 2 tools on it: read_file(path) and add(a, b), using the SDK's @server.tool()-style decorator (name may vary by SDK version).
  3. Run npx @modelcontextprotocol/inspector python3 server.py. In the inspector's web UI, manually call both tools and confirm you get correct results — this proves the server works standalone, with no agent involved at all.
  4. In your agent script, replace your local read_file/add functions with an MCP client that connects to server.py over stdio and forwards tool calls to it instead.
  5. Copy your module-03 run_evals.py and tasks.py in here unchanged, and re-run them against this MCP-backed agent.
check The identical server.py, unmodified, answers correctly both from the inspector's manual calls and from your agent's automated ones — and your module-03 eval suite still passes.
09

Production hardening

sensorcomputational

What

Idempotency keys derived from the underlying problem's state (not the trigger), so retries and re-deliveries don't double-act. A hard per-run and per-window token/cost ceiling that halts and escalates rather than looping silently. Metering every invocation — tokens, turns, outcome — so burn is visible on a dashboard, not the bill.

Why it exists

This is, near-verbatim, the guardrail list already sitting in your own CLAUDE.md — written after a real incident where an agent invoked as a pure function of a repeating alert burned ~11M tokens/day re-investigating the same unchanged state. The industry converged on the identical fix independently in 2026: dedupe on the problem, not the event.

🛠 Build

Goal Firing the same fake "alert" through your harness 50 times in a row costs roughly the same as firing it once — because the 49 repeats get recognized as unchanged state and skipped, with every attempt (run or skip) logged, and a hard ceiling that stops a runaway loop instead of letting it burn silently.
Environment setup 
mkdir -p ~/harness-course/09-hardening && cd ~/harness-course/09-hardening
cp ../02-tool-interfaces/*.py .
source ../01-bare-loop/.venv/bin/activate
python3 -c "import json,hashlib" # both are Python stdlib — nothing to install
Steps
  1. Define a fake trigger payload as a Python dict, e.g. {"alert": "disk_high", "host": "web-1", "value": 91}.
  2. Write problem_hash(payload): pick only the fields that describe the actual problem (not a timestamp or a trigger/event ID) and hash them with hashlib.sha256(json.dumps(fields, sort_keys=True).encode()).hexdigest().
  3. Before running the agent loop, check a small file seen_hashes.json (a dict of hash → last-seen time) for that hash. If it's already there, log "skipped: unchanged state" and return immediately without calling the model at all.
  4. If it's new, run the loop as normal, then record the hash in seen_hashes.json.
  5. Add MAX_TURNS = 8 inside your loop; if you exceed it, raise an explicit error ("circuit breaker: exceeded 8 turns") instead of continuing.
  6. Write one line per invocation to invocations.log: timestamp, tokens used, turns taken, and outcome (ran / skipped / breaker-tripped).
  7. Write a small test script that calls your harness with the identical fake alert payload 50 times in a row in a loop, then sums the "tokens used" column of invocations.log.
check Your test script's summed token total after 50 identical firings is barely more than after 1 firing — the steady-state cost test the real canary-agent incident (11M tokens/day on an unchanged alert) was missing.

Capstone: a coding agent in a box

guidesensorstructure

What

Every prior module wired into one system: loop (01) + well-designed tools (02) + sandboxed permissions (05) + sub-agents (06) + persistent memory (07), scored by the eval harness (03) you built in week one, hardened per module 09. This is, structurally, the same shape as Claude Code, Codex CLI, and SWE-agent.

Why it exists

Integration is where harness bugs actually live — a permission gate that blocks a subagent's legitimate write, a compaction step that drops a fact your memory system needed. You can't find those by testing modules in isolation.

🛠 Build

Goal One combined script pulling together modules 01–09, scored against 5 real bugs by your own module-03 eval runner — with a number proving it beats a plain one-shot API call with no tools at all.
Environment setup 
mkdir -p ~/harness-course/10-capstone && cd ~/harness-course/10-capstone
cp ../02-tool-interfaces/*.py ../03-eval-harness/run_evals.py ../04-context/*.py \
   ../05-permissions/*.py ../07-memory/*.py ../09-hardening/*.py . 2>/dev/null
source ../01-bare-loop/.venv/bin/activate
git clone <a small real repo you know well> target-repo   # or use SWE-bench-lite's dataset instead
Steps
  1. Pick 5 small, real, already-fixed bugs where you know the correct fix — from your own repo's git history (git log --oneline and find 5 one-line-ish fixes), or 5 tasks from SWE-bench-lite if you don't have a repo handy.
  2. Wire one combined script from the pieces you've already built: module-02's tool loop, module-05's permission gate around write_file/run_shell, module-04's compaction, module-07's memory folder, and module-09's idempotency + circuit breaker.
  3. For each of the 5 bugs: point the combined agent at the repo with a prompt describing the bug (not the fix), let it work inside the module-05 sandbox, and check whether the resulting diff matches the known-correct fix (or the relevant test passes) using a module-03-style checker.
  4. Run the identical 5 bug descriptions through one plain, single API call with no tools, no loop, no sandbox — just "here's the bug, write the fix" in one shot — as your baseline.
  5. Tally pass@1 (bugs correctly fixed out of 5) for both your full harness and the naive baseline.
check Report both pass@1 scores side by side. The gap between them is the number that proves your harness earned its complexity — not a feeling, a score.
